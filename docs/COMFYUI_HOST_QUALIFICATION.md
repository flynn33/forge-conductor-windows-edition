## Approval evidence and qualification categories

The harness uses `WindowsLMStudioConversationReader` against the actual selected saved LM Studio chat, including selected message versions and chronological positions. Its `final --plan <UUID>` command calls the same production service gate. It never manufactures an approval or a saved tool result.

Final approval requires a real saved `comfy_run` or `comfy_job_status` result from `mcp/forge-conductor` or `mcp/forge-conductor-fallback`. That result must contain the exact pending plan and sealed preview artifacts, and precede the subsequent operator reply. A plain harness preview is not a saved LM Studio tool result, so a subsequent `yes` alone cannot approve it. Do not modify native conversation files to bypass this condition.

| Evidence category | What it establishes |
|---|---|
| Deterministic fixtures | Graph, protocol, durability, permission and error contracts for the exercised fixture paths. |
| Native host harness | Actual installed-provider startup, frontend behavior, preparation or preview inference for the recorded request. |
| Real LM Studio model request | A real model requested the new tools through a configured integration; preserve the actual saved native call/result evidence. |
| Operator approval and final | A subsequent human reply passed the saved preview gate and the final produced verified required artifacts. |
| Operator quality acceptance | The operator accepted the visual result; technical completion alone does not establish this. |

Harness evidence starts with `lm_studio_request_verified: false` and `operator_quality_accepted: false`. A successfully completed preview sets only `host_preview_inference_verified: true`.
