**Work:** Implement or complete project-memory, continuity, combined and separately confirmed all-store maintenance. Coordinate live writers/leases and generations through existing services.

**Completion evidence:** The selected scope is explicit; reset cannot erase source repositories or another project accidentally; late old-generation work cannot recreate reset state.

### R4.5 — Settings accessibility and failure handling

**Work:** Exercise keyboard/focus, scaling/high contrast, invalid input, cancelled confirmation and repeat save/restart. Keep ordinary settings edits independent of administrative certificate trust.

**Completion evidence:** A practical GUI pass and concise readback/reset checks pass on disposable data.


## Implementation starting points
The Provider panel already loads/saves/probes typed settings; Settings still has a generic page. Build the complete usable Settings surface through the existing Manager settings/configuration/secure-storage paths. Discover which additional settings/maintenance services exist before adding contracts. Use the current confirmed repeated-save/ACL and automatic-model-null fixes; don't regress them while refactoring.

Expose endpoint, model selection, credential set/replace/clear where applicable, effective context capacity and reserves, shell preference, logging/telemetry preferences, Manager lifecycle/startup policy where supported, profile information and scoped maintenance. Settings may link to a dedicated Provider view; the operator should not edit JSON or browse D: to operate the product. Do not add network-provider scope solely because a form can accept an address; preserve supported LM Studio connection policy.

Use paired sliders and numeric entries for context controls. Validate total reserves against effective capacity and distinguish this application threshold from the actual loaded model context. Read the effective saved Manager values back after save; show pending/rejected edits and reconnect-required state. Never display a tool-count or elapsed-session budget.

Implement memory, continuity, combined and separately confirmed all-store maintenance through one native service coordinating active writers and generation fencing. The UI identifies exactly which project/profile is affected. Cancellation does nothing. Stop/fence appropriate old writers before clearing the chosen data and invalidate old-generation results. Do not delete repositories, treat another project's store as a cache, or perform destructive checks on the owner's live profile.

Add only needed persistence/validation/reset regression cases and perform a real keyboard/focus/scaled/high-contrast settings pass. Exercise valid/invalid and repeat save/readback, cancelled reset, A reset preserving B, and late-write rejection. All-stores testing needs a wholly disposable isolated profile. Administrative certificate trust is an installer concern and does not justify inaccessible ordinary configuration.
