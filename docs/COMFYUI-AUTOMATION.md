# Local ComfyUI automation

Forge's ComfyUI tool pack lets the Primary or Fallback model discover the local installation, build and edit workflows, resolve dependencies, and render image, video, or other file outputs. The operator describes the desired result in LM Studio. The model handles ComfyUI's graph and runtime details, presents a preview, and starts the sealed final workflow after the operator approves that preview in the native LM Studio chat.

This feature is part of Forge Conductor 1.3.29 / Windows package 1.3.29.0. The catalog has 125 tools: the prior 112, eleven ComfyUI tools, and desktop scroll/drag. The three existing LM Studio integrations remain the connection surface. [Versioned release verification](validation/RELEASE-1.3.29.md) and [actual host qualification](COMFYUI_HOST_QUALIFICATION.md) retain separate build/package and productive-inference evidence.

The existing `image_provider_status`, `image_generate`, `image_edit`, and `image_job_*` contracts remain separate. Use the ComfyUI tools for arbitrary local workflows and outputs. Do not mix an image job ID with a ComfyUI job ID.

## Configuration and authority

In Settings, enable ComfyUI automation and configure the installation, optional model storage directory, loopback endpoint, automatic setup, download budget, free-space reserve, generation timeout, and quality preference. An empty installation path asks the backend to inspect known local installation locations. An empty model storage path uses the installation's models directory. The default endpoint is `http://127.0.0.1:8188`.

Automation is disabled by default. Automatic setup defaults to enabled, the download budget to 500 GB, the free-space reserve to 50 GB, and the generation timeout to 1,800 seconds. The timeout accepts 1 through 7,200 seconds. Quality preference is `balanced`, `quality`, or `preview`; this preference is configuration evidence, and workflow dimensions, sampling, frame count, and other generation choices still belong to the graph.

Each operation belongs to the bound Forge project. User input, workflow, export, and output paths use the current authorized filesystem scope and must be absolute. Runtime files use Forge's private runtime directory; dependency destinations use the configured installation/model directories or Forge's managed components/custom-node directories. Runtime control, setup, and generation require current Execute permission and enabled shell policy. UI workflow conversion also requires Microsoft Edge execution. Discovery and read-only status do not grant execution permission. Settings changes and permission revocation are checked again during durable work.

Custom nodes execute inside the external ComfyUI interpreter with that process's host permissions. Forge's input/output authorization and artifact checks do not sandbox a custom node's internal filesystem, network, or process effects.

## Tools

All tools use MCP `tools/call` with their exact name and an argument object. The full schemas are in [the semantic catalog](../tests/fixtures/Mcp/mcp-tools-semantic-golden.json) and [the model capability inventory](LM-STUDIO-MODEL-CAPABILITIES.json).

| Tool | Arguments and result |
| --- | --- |
| `comfy_status` | No arguments. Reports configured endpoint, local installation observations, provider availability, queue, and managed process ownership when observed. |
| `comfy_catalog` | Required `kind`: `nodes`, `models`, `workflows`, or `templates`. Optional `name`, `category`, `filter`, `offset`, and `limit` (1–100). Node/model pages use `entries`; workflow/template pages use `items`. Follow `has_more` and `next_offset`. |
| `comfy_workflow` | Required `action`: `import`, `inspect`, `modify`, or `export`. Optional inline `workflow`, absolute `path`, and `patches`. Each patch has `node_id`, `input`, and `value`. Returns a serialized API workflow and its digest; UI conversion can also return `ui_workflow`. |
| `comfy_validate` | Required API `workflow`; optional `expected_outputs` node IDs. Returns readiness, node/input/link issues, and output-node evidence without enqueueing a render. |
| `comfy_prepare` | Optional `workflow`, `dependencies`, and `timeout_sec` (1–7,200). Starts a durable preparation job. Read the returned job ID until its result records the actual outcome. |
| `comfy_control` | Required `action`: `start`, `stop`, or `restart`; optional `timeout_sec` (1–7,200). Starts a durable lifecycle job. Stop/restart require verified Forge ownership and a drained provider queue. |
| `comfy_run` | Required `stage`: `preview` or `final`. Preview supplies `media_kind` (`image`, `video`, or `mixed`), both graphs, and an output directory. Final supplies only `stage` and `plan_id`. Starts or advances a durable plan; it returns before the render completes. |
| `comfy_job_status` | Required `job_id`; optional `wait_sec` (0–60). Reads the current durable state, provider facts, errors, and artifacts. |
| `comfy_job_list` | Optional `offset` and `limit` (1–100). Lists durable jobs in the bound project. |
| `comfy_job_cancel` | Required `job_id`. Suppresses local publication and reconciles the exact queued/running provider prompt. Active interruption requires verified provider ownership and an exclusive matching active prompt; inspect cancellation facts in status. |
| `comfy_job_resume` | Required `job_id`. Reconciles the recorded work after disconnection or restart. A render reattaches to its exact existing provider prompt; it does not submit a replacement render. |

API workflows are node-ID-keyed objects whose nodes have `class_type` and object-valued `inputs`. UI workflows are imported through a private Edge session and ComfyUI's frontend serializer. Patches change an existing API input or an existing serializable UI widget. Importing, inspecting, modifying, and exporting do not queue a render. An export chooses a new destination; it refuses to overwrite an existing file.

The template catalog's starter manifest returns absolute `preview_file` and `final_file` paths beside the installed Forge executable. These paths can be passed directly to `comfy_workflow` import; the manifest retains its parameters, input/output bindings, policies and qualification fields.

Literal array inputs use a single-key `{"__value__": [...]}` wrapper. The installed provider removes this wrapper during validation, so owned queue/history reconciliation accepts that exact removal at the same node/input while retaining the submitted graph and its hash in the receipt. Other graph changes remain errors. Preflight rejects raw literal arrays, wrappers with extra fields, and wrapped two-element arrays beginning with a string and followed by a number or boolean: the installed provider reinterprets that last shape as a link after unwrapping. A node's discovered input contract still determines whether a literal value is valid.

Single-key wrapped strings receive the same model discovery, installed-model identity and live enumeration checks as ordinary string inputs. Wrapping a model filename does not bypass missing-model preparation or readiness checks.

For observed desktop adjustments, `desktop_scroll` requires the current `window_id`, `pid`, window-relative `x`/`y`, and a nonzero `delta` from −12,000 through 12,000 wheel units. `desktop_drag` requires `window_id`, `pid`, window-relative `start_x`, `start_y`, `end_x`, and `end_y`; optional `duration_ms` is 50–5,000 and defaults to 500. Coordinates are bounded to 0–8,192. Both require execution authority, verify the window/PID, and check the foreground target before sending input; drag uses the left mouse button.

## Dependency preparation

Managed startup includes every enabled installed and Forge-managed custom-node package except ComfyUI-Manager. Manager's prestartup installer can run dependency repairs and queued installations outside Forge's preparation transaction, so Forge resolves dependencies through `comfy_prepare` under the installation lock. The installed Manager package exports no generation nodes; its local publisher/model mappings remain available to preparation. Forge does not disable ComfyUI's built-in API-node inventory or add a frontend network policy.

Preparation uses the existing portable ComfyUI interpreter. With automatic setup enabled, a workflow-only preparation inspects live node contracts and resolves missing dependencies from identified sources. Installed node/model choices are reused. Missing custom nodes are looked up through Comfy Registry's node mapping; an installed ComfyUI-Manager mapping can identify a unique publisher repository when the Registry lookup has no result. Active Registry packages are pinned to their concrete version and version ID. The fallback pins an identified GitHub publisher repository to an exact 40-character commit before downloading its archive. Ambiguous mappings, inactive publishers/packages, and unavailable provenance produce an actual preparation failure.

An import-failed node can reuse an enabled installed source after unique publisher discovery proves its existing Forge manifest, Git origin and resolved installed HEAD, or Registry project version and tracking file. Preparation pins the installed version or revision, seals that source and its publisher metadata, and inspects its declared requirements without downloading another node copy. A matching publisher does not establish successful import: readiness must still expose the requested class. Live `python_module` values bind to an exact directory or Python file across the stock, managed and operator-configured custom-node roots; ambiguous matches fail. Single-file nodes do not inherit their parent directory's requirements. Saved source bindings are checked before resumed preparation can change the installation. A legacy preparation that retained only nonempty source-directory paths requires fresh preparation because those paths do not prove the prior content. Final dependency identity reads the current publisher metadata and complete directory tree or Python-file content from the latest active binding for each source, including missing content. Git pins, configuration JSON and other node assets can therefore invalidate approval when code bytes are unchanged; Git internals and generated Python caches remain outside the directory tree and publisher metadata has its separate seals. These Stage28 paths have new native fixtures; linked execution and actual host qualification are reported separately.

Missing model names must have one matching entry in the installed Manager model catalog. Model discovery uses live enumeration contracts and catalog names without a filename-extension whitelist, and excludes declared image, audio and video upload widgets. A live model enum names the exact category-relative installed path; the catalog's preferred download subfolder does not relocate that existing selection. Qualified paths, missing files and wrong-category matches remain distinct. Category paths include literal stock folder mappings and absolute or relative paths in the installed `extra_model_paths.yaml`, including newline blocks whose physical directory names differ from their categories. Native projection applies the installed legacy aliases, ordered groups, default insertion and `base_path` user/environment expansion before appending Forge's configured storage roots; individual category paths are not environment-expanded. Supported YAML scalar blocks and quoted strings are projected, while unsupported nested mappings, flow collections and ambiguous scalar shapes fail explicitly. Runtime launch preserves the actual stock physical alias order, including `text_encoders` before `clip` and `unet` before `diffusion_models`. The original installation YAML is retained. The launch receipt seals its presence and content plus resolved ordered category paths; a later YAML or resolved-environment change prevents managed readiness, generation and artifact collection until the exact owned drained runtime is stopped and relaunched. Explicit stop/restart proves process and listener ownership separately from loaded configuration drift. The current automatic resolver supports publisher Hugging Face URLs: it pins the repository revision and reads the requested file's LFS SHA-256 and byte count before download. Default storage categories come from the installed Manager's literal model-directory mapping. Missing nodes and catalog-backed models can be resolved during the same preparation operation. It checks the live node's enumeration again after preparation. An unavailable repository reports its resolved source and HTTP status. This resolver does not cover every possible model host or arbitrary custom-node model-discovery mechanism, and model-path configuration with dynamic YAML constructs is unsupported.

Registry dependency declarations, custom-node `requirements.txt` files with local `-r` includes and `-c` constraints, declarative `setup.cfg` requirements and requested extras, and literal `pyproject.toml` project dependencies and requested optional extras feed package resolution. Preparation also inspects these declarations for already installed workflow nodes identified by the provider's actual `python_module` schema. Included files remain within the publisher source and retain their hashes. Forge runs fixed introspection through the selected interpreter's installed pip packaging implementation to evaluate requirement markers, extras, versions, interpreter compatibility, and wheel tags. Its installed resolvelib solver backtracks across compatible package versions, with publisher metadata fetched and budgeted by the native service. It reuses compatible installed packages, verifies resolved PyPI wheels against their publisher SHA-256 and byte counts, and checks the combined package requirements before activation. Installed runtime baseline versions, including Torch/NVIDIA packages, remain pinned; an incompatible runtime request produces conflict evidence. With automatic setup disabled, preparation can reuse verified dependencies and compatible baseline packages; it refuses missing nodes, models, media inspection components or packages before querying their publishers and does not activate staged wheels.

When a selected PyPI version has no compatible wheel, preparation can build its SHA-256-pinned source distribution through the installed interpreter's PEP517 hooks. Build-system declarations and hook-discovered build dependencies resolve separately from runtime requirements: compatible installed build tools are reused, and a different required tool version installs into an inactive build overlay. New source workspaces use the selected installation's `forge-builds.disabled/<operation UUID>/<attempt UUID>/project` directory so Windows tar and backend child processes receive bounded working-directory paths. Preparation checks the actual extraction and build directory lengths before those processes run and reports an installation path that exceeds the child-process limit. Native Forge fetches and accounts for source archives, build metadata and build dependency payloads. Build installation uses local sealed wheels with `pip --no-index --no-deps`; generated wheels retain the source archive identity, exact generated wheel SHA-256, metadata, source/build directory seals and bounded hook logs. Every hook invocation uses unique JSON result and log files so publisher stdout or stale prior-attempt results cannot replace a fresh result. A missing optional metadata hook falls back to one wheel build. Completed source builds can be reused after checking all retained content seals, including at an exhausted transfer budget; sealed legacy builds inside the same preparation transaction remain reusable. Build recursion is limited to three source-build levels and 128 retained source packages; failed attempts retain their evidence.

Each source hook saves an unverified baseline-inventory marker before dispatch and checks the installed runtime package inventory afterward, including caught process failures. Transient tar, pip and hook process trees terminate when their Manager owner exits; the provider runtime retains its separate durable process behavior. A changed or unverifiable inventory suppresses prior-runtime restoration; resume requires the exact saved baseline to reconcile that marker. The durable manifest, cumulative transfer ledger and downloaded publisher payloads stay in the preparation transaction. Source/build workspaces remain inactive, are scoped to that exact operation and do not activate through the runtime search-path file or enter the active custom-node source inventory. Reserve checks cover both the transaction volume and the actual source/build output volumes. Publisher build hooks still execute external source code with the interpreter's host permissions, just as custom nodes do; Forge's native transfer ledger covers its own resolved downloads and does not sandbox a hook's internal effects. Active direct URL/VCS requirements, requirement-file installer/index options, custom-node dynamic project dependency declarations, missing native build tools and unsupported source/archive contracts still fail explicitly. Arbitrary publisher `install.py` scripts are not executed by preparation. Offline synthetic hook and native interruption/reuse fixtures are distinct from actual custom-node installation and inference qualification.

Wheels install into a managed package overlay with `pip --no-index --no-deps`; native Forge performs their downloads and the installed interpreter performs package installation. The interpreter's search-path file activates the overlay. A video/audio workflow also prepares missing FFmpeg/FFprobe from a concrete BtbN FFmpeg Windows release asset when the publisher supplies its SHA-256 digest. The manifest records source revisions, package versions, download identities, transfer counters, package inventory, node revisions, configuration file identities, activation intent, readiness results, and rollback facts.

Explicit dependency entries remain available for identified sources outside these automatic resolvers. They require `kind`, `url`, `sha256`, and `target`. Kind is `model`, `custom_node`, `component`, or `package`; URL uses HTTP or HTTPS, checksum is a complete SHA-256 digest, and target is a safe relative path under the kind's destination. An optional `archive` flag requests extraction. Explicit custom nodes require an archive and an exact 40-character hexadecimal `revision`; packages require wheel files. Automatically resolved immutable Registry/GitHub packages also retain the SHA-256 actually measured after download, with a distinct manifest seal method when their publisher metadata did not supply a checksum.

The saved download budget counts received bytes across publisher metadata, payloads, wheels, redirect/error bodies, retries, and preparation resumes. Native preparation persists a receive admission of at most 16 MiB before reading in chunks of at most 64 KiB. `downloaded_bytes` records measured bytes; `uncertain_download_bytes` conservatively records an unresolved admission after interruption; `budget_charged_bytes` includes both and any current reservation. Retained staging growth is credited against its saved admission rather than charged twice. A completed transfer releases its unused reservation and retains its actual byte totals, including a completed HTTP error response. An interrupted legacy receipt still marked `preparing` receives a bounded uncertainty allowance for its last unsaved receive window; legacy failed/completed receipts and verified transfers retain their measured totals. A retry consumes only the remaining saved budget. Reusing verified content is permitted when the charge equals that budget. Installed-tree verification and archive expansion have an independent 64 GiB content bound, with bounded entry inventories; the download limit does not constrain the size of an already installed dependency or its expanded archive. Declared archive allocation and actual free-space checks still apply before and during extraction. Downloads allow a bounded HTTP or HTTPS redirect chain; scheme-relative redirects inherit the current URL scheme. Transfer accounting, checksum verification and staged publication apply to either scheme. Automatic publisher resolution retains the publishers' concrete HTTPS URLs.

Successful publisher metadata is sealed and reused. A negative response, including HTTP 404, 429, or 5xx, retains its status, response-body SHA-256, received bytes, and a bounded diagnostic. Resuming can make a new request with a separate evidence filename while retaining the previous attempt and its cumulative byte charge. A successful metadata response must contain valid JSON. These retry and response-document policies have deterministic fixtures; those fixtures do not establish an actual publisher-outage recovery on this host.

Free-space checks cover streaming transfers, staging, extraction, overlays, and cross-volume publication. A cross-volume file copy writes to a unique disabled sibling under the authorized destination directory. Native copying checks cancellation, deadlines, and the reserve before each chunk, verifies the source before and after copying, and verifies the staged destination's SHA-256 and byte count. Activation uses a same-volume atomic rename after another provider-idle check. Failed copies retain inactive staging evidence, with copied bytes measured from the staging file. The copy helper has fixtures for exact multi-chunk output, reserve failure, cancellation, and size rejection. Build21 also passed an actual native backend check that copied and sealed 4,194,321 synthetic bytes from C: to A: and verified rollback after an intentional fake-runtime readiness failure, with an unchanged transfer ledger. That check used temporary namespaces and did not install a real model or submit inference; its evidence is separate from image/video host qualification. Existing different dependency content is refused, and archives reject unsafe paths and link entries.

Both managed ComfyUI rendering and the existing image provider share a native provider-operation lease; preparation additionally holds an installation lock. Active dependency changes require either verified process and listener absence or a confirmed stop of an available, exactly owned runtime with a drained queue. Queue responses must contain both running and pending arrays; missing fields do not establish an empty queue. This check applies to recovery, each dependency activation, interpreter search-path changes, and active rollback. The prior interpreter search path is retained and restored on failure when it still matches the operation's replacement. Newly activated files/directories are retained in disabled locations during rollback. Changed or unsealed content, a busy queue, unavailable ownership evidence, or an unconfirmed stop causes active files to remain in place with unreconciled diagnostics and suppresses restoration of the prior runtime. Poll the preparation job and inspect its actual outcome and `manifest_path`; the public result omits the full manifest so polling remains bounded. Starting a preparation job does not establish successful installation.

For the installed portable interpreter, source builds use an inactive copy of its executable and runtime DLLs inside the build overlay. Native streamed copies verify the installed component hashes and check available space before each write. The copy's search paths retain the original runtime and add the prepared build dependencies; a fixed `sitecustomize` processes their `.pth` files for spawned child interpreters. Build dependency wheels also install through that copy, so generated console launchers select the same build environment. Reuse checks the copied components and generated configuration against their retained content. The provider's installed interpreter files remain the baseline used for package-inventory checks.

## Preview and final generation

The model first discovers actual node contracts and model choices, imports a suitable workflow or constructs an API graph, and validates both the preview and final graphs. A video graph can use local video output nodes; image generation uses image output nodes. Available nodes and models determine which workflows the local installation can execute.

The preview request supplies these fields:

```json
{
  "stage": "preview",
  "media_kind": "video",
  "preview_workflow": {"...": "discovered and validated API nodes"},
  "final_workflow": {"...": "discovered and validated API nodes"},
  "output_directory": "D:\\ForgeProjects\\Video\\renders",
  "inputs": [{"node_id": "12", "input": "image", "path": "D:\\ForgeProjects\\Video\\source.png"}],
  "preview_expected_outputs": ["25"],
  "final_expected_outputs": ["25"],
  "timeout_sec": 1800
}
```

The workflow values above are placeholders showing the request shape; use real API node objects. `inputs` contains at most 64 distinct local source bindings. The input name defaults to `image`. Every binding must target an existing node input in both graphs. A literal file input whose discovered required or optional schema declares `image_upload: true`, `audio_upload: true` or `video_upload: true` requires an explicit local binding, including filenames already listed by ComfyUI. Preflight reports these as `provider_file_inputs`; managed rendering cannot use an unsealed existing provider file. `expected_outputs`, `preview_expected_outputs` and `final_expected_outputs` contain exact output node IDs: `["25"]` selects node `25` in the corresponding graph. Set file names in that output node's inputs. `expected_outputs` is an optional common alias when a stage-specific output list is absent. An empty effective list infers all output nodes from the graph and checks them against the provider's node contracts.

The model reads `comfy_status` for effective limits and default quality before selecting creation settings. If the operator omits video duration, it proposes a motion draft of about five seconds. It chooses playable MP4/H.264 for final video from discovered output-node contracts unless the operator requests a supported alternative format or codec. The selected format belongs in the proposed final graph before preview approval; changing it later requires a new preview and approval. Supported requested alternatives are preserved. Unknown graphs do not receive a universal output-format rewrite.

Before requesting image-preview approval, the model calls the existing `image_read` tool with the verified preview image artifact's `path` to display a larger bounded image. The native build30 image request returned a 68×68 job-status thumbnail for a verified 512×512 PNG; the thumbnail alone was insufficient for reviewing that image, and the model supplied only its path. `image_read` uses its existing adaptive preview limits; this delivery guidance changes no tool arguments or image allowance. The build32 native LM Studio image request used this guidance and delivered a saved 384×384 preview alongside the verified 512×512 artifact path and proposed final settings. Both files were visually inspected; the plan remains awaiting a real operator reply. See [host qualification](COMFYUI_HOST_QUALIFICATION.md) for the recorded evidence and remaining acceptance checks.

Successful decoding establishes readable media, not whether the requested subject appears or its motion meets the request. Before describing video content or quality, the model calls the existing `image_analyze` tool with the `path` of the published artifact whose `role` is `sampled_video_contact_sheet` and polls `reviewer_status` for actual findings. Missing contact sheets and review failures must be reported with the returned errors. Visual claims are limited to reviewed sampled frames; the prompt alone is not evidence of observed content, and sampled frames do not establish full motion quality. The operator still reviews the actual playable preview for approval through the existing chat reply.

Published provider files also retain `provider_view_url`, the exact local ComfyUI `/view` URL used to retrieve them. For a verified video preview or final artifact with this URL, the model calls the existing `browser_open` tool with the exact URL while ComfyUI is running, then uses `desktop_read` on the observed browser window to check its actual address. Launch acceptance alone does not verify page loading or playback; report actual browser-launch or observation failures. Present the URL as a copyable reference, the complete `artifacts[].path` in a copyable fenced block and the sampled-frame preview without abbreviating file paths. Derived local contact sheets have no provider URL. The installed LM Studio 0.4.26+4 ordinary Markdown link path calls `openExternalURL` and `isValidExternalURL`, which rejects loopback hostnames; the host log recorded rejection of the exact saved ComfyUI video URL. Its classic-chat renderer also strips Windows file protocols from Markdown links and uses an image preview component. These observations require browser delivery through the existing Forge tool, rather than assuming a clickable Markdown playback link. Independent sampled-frame review and real preview approval remain required; browser loading and playback need their own observed evidence. See [host qualification](COMFYUI_HOST_QUALIFICATION.md) for the installed-source and runtime evidence.

The Manager uploads source files, seals the original and private provider-copy bytes and SHA-256 hashes with their exact node/input bindings, gives output filename prefixes a project/job/stage namespace, preflights both graphs, and submits the preview under a recorded prompt ID. It rechecks both copies before submission; a changed provider copy invalidates final approval even when the original local source is unchanged. Automatic setup may start the local runtime and resolve missing dependencies within its limits. Job snapshots expose the persisted phase, including `uploading_inputs`, `preflight`, `preparing_dependencies`, `sealing_dependencies`, and `waiting_provider_queue`. After waiting for unrelated provider work, the service rechecks dependencies before submission. Terminal states override a stale phase; older receipts without a phase use their saved state. Poll the returned job ID until `state` is `awaiting_preview_approval`, or inspect the recorded error if it fails.

The completed preview contains an `artifacts` array and retained preview artifact evidence. Public job snapshots, list pages, and catalog pages are capped at 128 KiB before transport encoding; aggregate inline previews are capped at 32 KiB. Public artifact metadata includes bounded measured fields such as dimensions, duration, frame count, codec, and decode status. Full preparation and media-inspection evidence remains in the durable receipt and referenced manifests. An individual artifact collection or catalog entry that cannot fit produces an explicit size error rather than silently dropping result links or schema fields. A motion-intent preview must decode as video, GIF, APNG or animated WebP with positive duration and at least two frames before it can reach approval; static images and missing decoder evidence fail explicitly. Mixed plans also require motion when an intended preview or final output has a `VIDEO` node contract, a connected `VIDEO` output, or an actual selected `video/` format enum. The preflight reports these nodes as `motion_output_nodes`; each saved stage retains its intended motion-node IDs and requires a decoded playable motion artifact from every such node before completion. A suitable preview may use different output nodes from the final graph. Earlier version 1 interrupted receipts recover these stage contracts from the actual installed schemas while reattaching to the existing prompt ID. It does not infer motion intent from custom node names. It separately returns `media_inspection_required` for those contracts and the installed core `SaveAnimatedPNG` and `SaveAnimatedWEBP` outputs. Automatic setup prepares missing inspection components before submitting either saved stage, even when an image plan already passes inventory preflight. Present those actual files to the operator. Use file inspection and the existing independent image analysis tools when the model needs to assess image content. A preview displayed by LM Studio does not establish that pixels reached the chat model.

Present the returned `approval_reply_choices` with the actual local preview before waiting. After reviewing it, the operator replies `approved`, `yes`, or `render final` in LM Studio, ignoring case and surrounding punctuation or whitespace, including smart quotes. The service requires the latest saved native `comfy_run`, `comfy_job_status` or `comfy_job_resume` result awaiting approval before that reply to identify the same plan and exact preview artifact hashes. Presenting another plan's preview supersedes the previous preview for that reply. It checks the admitted conversation, saved message/version positions, and the unchanged prior conversation prefix. A reply sent before the preview result is delivered cannot approve it. The native reader excludes the reserved continuity-message prefixes emitted by Forge; it does not infer human authorship for every other saved user message. Model-provided approval flags are unsupported. The exact reply `verified` acknowledges delivery but does not approve final rendering or request a creative change. Any other real user reply after the saved preview boundary that does not match an approval choice durably invalidates that pending plan, even if a later reply says yes. Its snapshot returns `requires_new_preview: true`, `requires_operator_approval: false` and no approval choices, while retaining its preview artifacts and bounded message position/version evidence. A fresh revised preview can receive a new approval. An edited earlier message, changed source/preview file, changed provider configuration, or changed dependency identity also requires renewed preview evidence.

A later chat can recover a pending plan by presenting its verified preview through those existing native tools. Final admission reads the original saved conversation and checks its unchanged user prefix and any unobserved revisions. The current chat's latest preview receipt must match the saved job, project, revision, preview and final graph seals, bounded dependency evidence, and every artifact's node, media type, path, byte count and SHA-256. A genuine approval after that delivery can finalize the same saved plan without asking the operator to repeat it in the older chat. Recovery and approval evidence are persisted with the final receipt; the service still checks the complete live dependency identity and original/private input and preview files before submission. A continuity packet without an actual delivered preview retains the existing fresh-approval requirement. Neither recovery nor final admission sends a user message or changes creative parameters.

The final request is deliberately small:

```json
{"stage":"final","plan_id":"the UUID returned by the preview job"}
```

Final submission uses the sealed final graph and output intent from that plan. Workflow arguments and options cannot replace it. A verified continuity successor must recover the plan through native `context_get` evidence matching the handoff, project and plan token. Before rebinding, the service verifies the saved predecessor conversation's user-message prefix, selected message versions and replies after the preview boundary. A missing or edited predecessor persists `preview_recovery_requires_new_preview` and exposes `requires_new_preview: true` without approval choices. Successful recovery establishes the successor's approval boundary and requires a new operator approval there.

## Output and recovery facts

Successful collection checks the recorded prompt ID and graph against provider history, requires every intended output node, and publishes files under the authorized output directory's `preview` or `final` subdirectory. Artifacts can be images, video, audio, or other files. Each artifact records its node, local path, byte count, SHA-256, and media type. Video/audio delivery requires authorized FFprobe metadata and an FFmpeg full decode check; missing components can be prepared automatically as described above. A generic artifact is not an automatic claim that its visual content meets the operator's request.

If publication fails after moving a file, the collector retains the file and records the observed destination and staging state. The durable `collection_outcome` contains `publication_evidence`, counts of verified published files, uncertain publications and verified staging files, and a batch `publication_manifest` path and SHA-256 when that manifest can be verified. Public snapshots bound this evidence and retain its counts and manifest reference when truncation is necessary. Failed collection suppresses `artifacts[]`; a retained file or a partial publication does not establish successful completion.

Generic ComfyUI still-image inspection reads complete WIC pixel data in bounded strips and produces a reduced preview. It accepts at most 32,768 pixels per dimension and 268,435,456 decoded pixels. Animated PNG and WebP use external FFprobe and complete FFmpeg decoding, including measured frame count and duration. These limits belong to the generic ComfyUI path; legacy image decoding retains its existing contract.

Container MIME types use observed content identities. MOV and MP4 are distinguished by FFprobe's four-byte `major_brand`, with recognized 3GPP and 3GPP2 brands retained. Matroska and WebM are distinguished by the actual EBML Header `DocType`, parsed within a 1,024-byte prefix bound. Shared FFprobe demuxer names and filename extensions do not decide these types; missing, conflicting, malformed or unrecognized identities prevent verified publication.

The plan records workflow hashes, source and preview file hashes, configuration, and a dependency identity based on node schema hashes, source/package seals, and the content SHA-256 plus file identity, size and modification time of referenced local model files. It hashes the models selected by the saved graphs. Changes detected before final submission invalidate the plan.

The version 1 receipt retains full JSON evidence alongside a validated typed job, artifact, and render-plan core. Recovery rejects unknown states, mismatched job/plan IDs, malformed prompt IDs, scope fields, artifact paths/hashes/byte counts, and inconsistent graph or approval seals. An interrupted `before_dispatch` receipt may lack seals created during later execution; it remains observable as interrupted work. A render without an existing sealed prompt ID cannot resume by creating another provider submission. Receipt SHA-256 and the saved graph and file seals remain checked during recovery.

After a Manager restart, `comfy_job_list` and `comfy_job_status` expose retained jobs. For Comfy tool calls from a connector that remains running, a preliminary Manager status failure with a closed transport or connection deadline can use the existing Manager startup helper while the caller's operation remains active. It repeats status and the existing package/profile checks before sending the requested invocation once. A written invocation is never replayed; its failure remains observable so the model can recover the exact saved job. This recovery uses the existing startup path and adds no configuration or authentication method. List pages report missing, corrupt or inaccessible receipts in `unreadable_jobs` with their exact job IDs, receipt paths and errors, and set `partial` for that page. These rows consume the page's count and byte limits, so one unreadable receipt does not block recovery of other jobs. Public status and list pages limit inline evidence and preserve references to the durable receipt; follow `next_offset` when a list or catalog page has more entries. A byte-limited page can contain fewer entries than its requested `limit`. An interrupted submission can be `unknown`; use `comfy_job_resume` to inspect the exact recorded prompt. A missing acknowledgement is not permission to submit the graph again. A known rejected or failed provider execution remains failed and is not resumed as uncertain work. Cancellation only targets the exact owned queued/running prompt when identity and graph observations agree. An unowned ComfyUI runtime is never stopped by the lifecycle tools.
