# Forge Conductor 1.3.12: observable process work and verification evidence

Version 1.3.12 adds tools for owned long-running work, live output, host/provider inspection, GitHub reads, authorized external evidence, pinned verification dependencies, and independent reviewer runs. Primary and Fallback advertise 80 tools; CLU retains its five governance tools. Product identity is 1.3.12 and the corrective MSIX version is 1.3.12.1.

## Evidence and cause

The October 5 investigation found successful instruction-package and policy reads followed by repeated validation failures. The installed Primary trace records a wrapper returning `timed_out=true`, exit code 1460, and elapsed time 120,015 ms; its expected run receipt was absent afterward. Separate unit-test probes were terminated near their configured deadlines. In 1.3.11, `WindowsShellService::execute` caps execution at 120 seconds and `WindowsProcessSupervisor` owns the complete process tree in a terminating Windows job. Starting a child inside that bounded call cannot extend the lifetime of the owned tree.

The scheduled-task workaround observed a null `USERNAME` in the shell child environment. A separate Python wrapper failed UTF-8 decoding on byte 0x97 after its inner command reported exit 0. The repair supplies explicit safe profile/account values and UTF-8 Python defaults; this does not establish the encoding of every external executable.

The external `fs_write` failure followed the registered workspace boundary. Additional roots now require an exact existing owner-configured allowlist entry and an explicit binding call. A model request cannot grant arbitrary filesystem access. The investigation record is [LM Studio workflow repair evidence](../validation/LM-STUDIO-SHELL-JOBS-1.3.12.md).

Installed integration qualification found that the initial 1.3.12.0 broker forwarded MCP's unlimited session deadline into a Manager pipe with a five-minute request bound. Process and reviewer starts were rejected before execution. Revision 1.3.12.1 bounds the broker exchange to that existing pipe limit while preserving the original operation identity, cancellation, and any shorter caller deadline. The job's separately requested lifetime is unchanged.

## Process and output workflow

Start the task's complete original command through `process_launch`, providing the executable in `command`, an exact string array in `args`, the task's real `cwd`, and any required explicit `env`. Keep `job_id`. Use `process_poll` every five seconds or longer, or `process_wait` with at most 30 seconds per call. Waiting timeout returns a still-running job and does not kill it. Use `process_read_log` with `stream` (`stdout` or `stderr`) and either `tail_lines` or `offset`; follow `next_offset` while `has_more` is true. A status request's top-level `ok` does not prove command success. Require terminal state, actual exit status, timeout/cancellation/termination information, and the required reports before claiming completion.

When a final result is present, job status responses return stdout previews of at most 16 KiB and stderr previews of at most 4 KiB. The `stdout_capture_truncated`/`stderr_capture_truncated` flags describe result capture; `stdout_response_truncated`/`stderr_response_truncated` describe the smaller MCP preview. Named raw logs have their separate 16 MiB per-stream bound and `log_truncated` flag; use `process_read_log` for their retained contents. Its `text_lossy` flag identifies display substitution or alignment for binary/invalid UTF-8 bytes; the raw log bytes and their digest evidence remain unchanged. `process_list` summaries omit `args` and bound `command` to 256 UTF-8 bytes, with `command_truncated`; inspect the individual job for its full arguments.

Manager-backed jobs survive MCP reconnects while their owning Manager remains running. Job receipts and logs are retained, and adoption verifies their integrity and process identity. An interrupted broker cannot reconstruct a missing exit code as success. Unbrokered standalone jobs remain owned by their connector and are cancelled on that owner's shutdown. Maximum duration is 3,600 seconds, with two active jobs and sixteen retained results in shell-service memory. Durable storage retains up to thirty-two jobs per project. Named logs are capped at 16 MiB per stream; each log read returns at most 32 KiB. Check `broker`, job state, and returned lifetime facts rather than assuming that every composition has a persistent Manager.

Shell children receive explicitly constructed account/profile information and Python UTF-8 stream defaults. Exact argv avoids encoding a large wrapper inside `shell_exec`. This does not change the task's required full suite, receipt format, review authorization, or completion gate.

## Authorized roots and evidence

Inspect `workspace_authority` in `get_forge_status` for configured and active roots. The owner must already have placed an additional directory in saved `allowed_roots`; then the model can call `workspace_authority_bind` with its exact existing path. Binding is project-scoped and process-local, coordinated with the Manager for brokered operations. After a restart, bind the configured root again. A narrowed capability cannot use binding to recover removed grants. Overlapping roots fail without replacing the working authority.

Call `evidence_digest` with one to 64 authorized file paths. It streams binary bytes through retained authorized Windows handles and returns canonical paths, SHA-256 values, byte lengths, capture identity, sequence, and head digest. Limits are 32 KiB aggregate input/canonical path text, 64 GiB per file, 128 GiB per capture, and an 8 MiB durable project log. A full or malformed log fails without overwriting existing evidence. `evidence_log_read` defaults to verifying the full chain and supports offset/limit record pages, with at most sixteen records and 256 KiB per page.

The capture chain is unkeyed SHA-256. Keep the returned head digest independently to detect replacement and rehashing of the complete chain. It is an integrity record, not a signer identity or protection against a privileged owner rewriting every record and the retained head. Setting `verify=false` reports `not_verified`.

## Verification environment and reviewer

Create a dedicated verification venv below a bound additional root, outside the main source root, using `verification_env_create`. Pass the actual `python_path`, destination `path`, and the supported requirements `jsonschema==4.25.1` and `PyYAML==6.0.3`. Creation refuses an existing destination, installs binary wheels, checks the selected pins, and writes `verification-env.json` only after success. Follow its process job to successful completion, then read `verification_env_status` for the observed Python executable/version and installed distributions. Capture that manifest if the task needs durable dependency evidence. The venv isolates verification dependency writes and records exact observed versions. It is not an operating-system sandbox and does not make an arbitrary verification command read-only.

`reviewer_start` reads an authorized nonempty opening-message file of at most 64 KiB and starts a fresh Manager-owned provider session without executor conversation history. Tool calls are constrained to the read-only reviewer route. The caller's review authorization reference is recorded context, not proof of a human grant; the returned authorization facts identify the authenticated same-user Manager and project-scoped invocation. The caller remains responsible for the task's actual review authority and verdict contract.

Reviewer runs use a dedicated SHA-256-verified atomic receipt store that preserves the full task, provider state/usage, errors, pending calls, and output. Admission is capped at sixteen persisted receipts; when full it refuses a new run until the owner explicitly archives or deletes receipts. It does not silently discard earlier review evidence. Reports are capped at 256 KiB and expose `output_truncated` when that bound is reached; encoded receipts are capped at 4 MiB each. Loading an interrupted running receipt marks its outcome unknown and failed, retains pending-call evidence, and never replays those calls. Use `reviewer_status` for actual state and output. Each response returns at most 32 KiB of the retained report; pass `next_output_offset` as the next `output_offset` while `output_has_more` is true to read the full report, up to its 256 KiB bound. `output_page_truncated` describes paging separately from the report's `output_truncated` flag. Failure, cancellation, truncated required evidence, or executor self-review does not approve an independent gate.

## Context and completion readback

Inspect `get_forge_status.context_telemetry` for `measurement_scope`, `generation_reference`, `tokens_used`, `context_capacity`, `reserved_tokens`, `headroom_tokens`, and the observation time. This sample comes from the selected native chat's latest completed provider generation. Tokens added after that generation are not measured; absent observations return unavailable/null values with a reason. It is not a live exact count of every subsequent chat message. Reserve-pressure handling uses these observed provider statistics and reports overflow/tool activity.

`auto_continuity.readback_confirmed` compares the current resume packet with the handoff ID retrieved through `context_get` by this MCP client; `readback_scope` states that boundary. Packet storage, status retrieval, and memory attachment are separate facts. Check the job's `memory_attached` value and use memory/status readback when the task requires a persisted completion record. Preserve the complete original command, required reports, and reviewer verdict before applying a completion gate.
