## Native acceptance exposed a separate path failure

Separate native conversation `Forge-Conductor-Windows-Edition/1791223961132.conversation.json` completed nine Qwen calls. The three policy pages returned valid JSON at 32,516, 32,616, and 4,875 bytes and reconstructed all 270 coverage entries exactly. Pinned instruction text (1,808 bytes) and `AGENTS.md` (14,019 bytes) matched their saved hashes. However, `shell_exec` with the legitimate `D:/GitHub/YWE` cwd returned `invalid_request`: `An app-owned path must be a canonical absolute drive path.` The UI marked the protocol call successful; the actual payload was a failure. Consequently this native acceptance did **not** pass overall, and large shell reconstruction was not qualified by that chat.

`WindowsWorkspaceAuthority::resolveRequestedPath` passed the unnormalized user request directly to strict app-owned storage validation, which rejects `/`. The fake shell contract already accepts `D:/workspace`, so actual Windows authorization was inconsistent with the exposed contract. A new actual-process regression reproduced the same failure against this exact 1.3.10 CLI, after confirming the native separator variant worked. The next [1.3.11 release](1.3.11.md) repairs the requested-path boundary while retaining strict configured roots and scope protections.
